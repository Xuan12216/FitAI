## 發現（依優先順序）

### P1：沒有重量的「每份」被轉成看似精確的每 100g

位置：`WebNutritionScraper.kt:222-228`。

當來源只有「每 1 個／份」而沒有克數時，程式將較小的每份營養值直接當作每 100g，較大的則用熱量及巨量營養素推估重量，這些結果仍被當成可用的每 100g 樣品。現有 NutritionPortionCalculator 之後會據此自動換算克數。

重現：同一個 90 kcal 的測試樣品，來源寫「1个」得到 90 kcal/100g；來源補上「1个(50克)」則得到 180 kcal/100g。最終輸入 200g，分別產生 180 與 360 kcal。來源未提供重量時不應製造每 100g 數值，應保留每份基準或排除克數自動換算；毫升與克也不能一律視為相同單位。

### P1：內建資料把不同餐點／配方列成同義詞

位置：`TaiwaneseCommonFoods.kt:95,111,114,118`。

直接呼叫目前名稱比對，可重現：

- 麥香魚 → 麥當勞勁辣雞腿堡。
- 低脂鮮奶 → 全脂鮮奶。
- 無糖鮮奶茶 → 描述為微糖的鮮奶茶。
- 滷海帶 → 滷豆干。

這些別名會以精確別名分數進入參考候選，網頁未命中或離線時尤其明顯；指定克數後程式也會依錯誤樣品計算，模型無法補回不存在的正確原始資料。應拆成不同樣品，無可靠資料時降為明確的近似估算，不要當同義詞。

### P2：只要兩個字重疊，就接受不同餐點的網頁數據

位置：`WebNutritionScraper.kt:168-170`。

HTML 重現：查詢「牛肉麵」可以接受名稱「牛肉酱」的列，因為兩者都有牛、肉。此類未完整匹配的結果仍有分數並可進入網頁優先候選，後續低容量模型與無效樣品 ID 的備援可能更直接使用它。應要求核心餐點及必要修飾詞一致，不能只用不具順序的兩個重疊字判定；保留品牌及食物型態約束。

### P2：改為 BottomSheet 後沒有保留摺痕避讓

位置：`ManualMealDialog.kt:94-99`，同樣影響 `WeightTrendDialog.kt`、`ChatMealDraftDialog.kt` 與 `WorkoutSessionTools.kt`。

原先 AlertDialog 會呼叫 AdaptiveDialogPlacement；新 ModalBottomSheet 沒有接上 LocalAdaptiveInfo 或 separating hinge 的安全區邏輯。核對本地 Material3 1.5.0-alpha23 原始碼，預設是相對整個視窗置中，並非依 App 的摺痕安全區配置。半折且 isSeparating 的垂直／水平摺痕狀態下，表單可能跨過摺痕或被遮擋。應讓 Sheet 依可用 pane 佈局，或在該狀態使用已適配的對話框。本項為程式與依賴原始碼確認的回歸，未做新版實機摺痕操作。

## 其他觀察

- 新增的 72 筆外食數據在程式內沒有附逐筆來源或查證日期；來源對話框仍對內建資料提供食藥署連結，無法用該連結核對這些特定外食／品牌數值。
- 網頁結果只保存臨時編號及描述，沒有保存實際項目 URL；「查看 FatSecret 爬蟲來源」會重建搜尋網址，不是打開當時的原始營養頁面。
- 合併結果每次以現在時間建立 fetchedAt，fromCache 也只看網頁記憶體快取，未保留 TFDA 真正下載時間；顯示的檢索時間無法用來判斷各來源資料的新鮮度。
- 網頁爬取位於本地參考資料之前，無網頁快取的查詢，即使 TFDA 快取／內建資料可用，也會先等網頁。整體 20 秒期限涵蓋整段查詢，需補外網緩慢時本地備援可用性的測試。
